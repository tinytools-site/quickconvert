What is a UNIX timestamp?

A UNIX timestamp (also called epoch time) counts the seconds elapsed since 00:00:00 UTC on 1 January 1970 — the 'epoch'. For example, 1790860800 represents 1 October 2026. Because it is a single number with no time zones, no daylight saving and no formatting ambiguity, it is the standard way computers store and exchange moments in time.

You will meet timestamps in API responses, databases, log files and JWT tokens. They come in two flavors: seconds (10 digits, e.g. 1790860800) and milliseconds (13 digits, e.g. 1790860800000, common in JavaScript where Date.now() returns milliseconds). Mixing them up is a classic bug — a millisecond value read as seconds lands tens of thousands of years in the future.

This converter accepts either flavor and detects it automatically, then shows the moment as both a UTC date and your local date and time. Going the other direction, pick any date and time to get its epoch value in seconds — handy when an API expects a timestamp parameter.

One famous edge case: the 32-bit 'Year 2038 problem', when signed 32-bit timestamps overflow. Modern 64-bit systems are unaffected. All conversions here run locally in your browser with full 64-bit precision.

Frequently asked questions

What is the current UNIX timestamp?

Click the 'Use current time' button on the converter above — it shows right now as both seconds and milliseconds.

What is the difference between seconds and milliseconds timestamps?

Seconds timestamps have 10 digits (e.g. 1790860800); milliseconds have 13 (e.g. 1790860800000). JavaScript's Date.now() returns milliseconds. This tool auto-detects which one you pasted.

Why does my timestamp show the wrong date?

You probably mixed up seconds and milliseconds, or the timestamp is in a different unit (some systems use microseconds). Check the digit count: 10 = seconds, 13 = milliseconds.

What is the Year 2038 problem?

On systems that store timestamps as signed 32-bit integers, time overflows on 19 January 2038. Modern 64-bit systems and this converter handle far-future dates without issues.
